# 1年ぶりに触る自分へ

**上から順に読んで、書いてあるコマンドをそのまま打てば戻れます。**
最初にやることは「直す」ことではなく、**いま何が起きているかを確かめる**ことです。

しばらく離れていても、たぶん動き続けています。壊れていたとしても、
**集めたデータは git の中にあるので消えていません。**

## 1. まず、何が起きているか確かめる

GitHub Actions が毎朝6時（日本時間）に、集める→作る→公開する、を全部やっています。
まず**それが続いていたのか**を見ます。

### ① サイトは生きているか

https://raidock.github.io/iwami-goyomi/

開いて催しのカードが並んでいれば、公開は生きています。

### ② ボットは動いているか

```bash
cd ~/App/iwami-goyomi
git pull
git log -1 --format='%ad  %an  %s' --date=short --author=iwami-goyomi-bot
```

`chore: 収集 YYYY-MM-DD` の日付が**昨日か今日**なら正常です。
何か月も前で止まっていたら、収集が止まっています（→ 下の「動いていなかった場合」）。

### ③ 情報源は壊れていないか

```bash
python main.py health
```

情報源が全部 `✓` なら正常です。`✗`（0件）があれば、その市町のサイトの作りが
変わった可能性があります。

**このコマンドはその場で取りに行きません。** 最後の収集の記録（`out/health.json`）を
読むだけです。だから**先頭の「最終確認」の日付も見てください。**
そこが古ければ、壊れているのは情報源ではなく収集そのものです。

### ④ 承認待ちが溜まっていないか

```bash
python main.py status
```

承認待ちが何百件あっても壊れてはいません。**放置した分だけ溜まっただけ**です。
上から順に見ていけば片付きます。

### 動いていなかった場合

GitHub の画面を開いて、赤いバツを探してください。

https://github.com/raidock/iwami-goyomi/actions

- **赤いバツがある** → クリックすればどこで落ちたか出ます。
  過去には**ワークフローのファイルが3行欠けて2日間止まった**ことがあります
- **そもそも実行が1件も並んでいない** → GitHub は、**リポジトリに60日間さわらないと
  定期実行を止めます。** しかもボットのコミットは「さわった」に数えてもらえません。
  Actions の画面に `Enable workflow` のボタンが出ていれば押してください
- **実行はあるが遅い** → GitHub のスケジューラは混雑時に遅れることが知られています。
  60分前後の遅れはふだんから起きます（2026-08-07は約4時間遅れて動きました）。
  **半日以上動かなければ**手で1回動かすことを考えてください。それより短い遅れは
  様子を見るだけで十分です
- 直したら、Actions の画面の `Run workflow` から手で1回動かせます

## 2. 動く状態に戻す

`.venv`（Python の部品置き場）は git に入っていません。**新しいマシンや1年後の
環境では作り直しが要ります。**

```bash
cd ~/App/iwami-goyomi
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

- 部品は4つだけです（requests / beautifulsoup4 / lxml / PyYAML）
- **Python が新しくなっていても、たいてい動きます。** 2026年8月の時点で手元は
  3.11、GitHub Actions は 3.12 で、同じコードが両方で動いています
- 途中で失敗したら `rm -rf .venv` で消して、上からやり直してください
- **ターミナルを開き直すたびに `source .venv/bin/activate` が要ります。**
  以下のコマンドは全部、これを打った状態で実行します

戻ったかどうかの確認:

```bash
python main.py status
```

バージョンと件数が出れば戻っています。

## 3. いつもの作業（1日5分）

日常の運用は**承認だけ**です。これだけ覚えていれば回ります。

```bash
cd ~/App/iwami-goyomi
source .venv/bin/activate
git pull
python main.py review
git add data && git commit -m "chore: 掲載を承認" && git push
```

`review` は1件ずつ聞いてきます。

```
[y]公開  [n]捨てる  [s]あとで  [q]終了
```

**迷ったら `s`（あとで）で構いません。** `n` で捨てたものは二度と出てきませんが、
`s` は次も出ます。

**判断の基準は、一言でいうとこれだけです。**

> **横断して集めることで価値が出るか。**

浜田の人が江津の祭りを知りたいから、9市町を集める意味があります。
断水・通行止め・ごみ収集は、自分の町のことしか関心がなく、市の公式サイトを見れば
済むので載せません。ほかの基準は `CLAUDE.md` の「譲れない設計判断」にあります。

push して数分待てば、サイトに反映されます。

## 4. おかしいときに見る場所

### コマンド一覧

| コマンド | 何をする |
|---|---|
| `python main.py review` | 1件ずつ承認する（**日常はこれだけ**） |
| `python main.py status` | 承認待ち・公開中・却下済みの件数 |
| `python main.py health` | 情報源が生きているか（最後の収集の記録を読む） |
| `python main.py pending` | 承認待ちを一覧で見る（承認はしない） |
| `python main.py collect` | 集めて仕分けて承認キューへ入れる（毎朝ボットがやる） |
| `python main.py build` | 承認済みから公開サイトを作り直す |
| `python main.py audit` | 情報源の在庫と突き合わせ、載せ落としを探す（月1回・読むだけ） |
| `python main.py dedupe` | 重複を掃除する（ふだん使いません） |

### テストを全部走らせる

```bash
for f in tests/test_*.py; do echo "== $f"; python "$f" || break; done
```

全部通れば、コードは1年前と同じように動いています。
ただし**テストが緑でも事故は起きます。** このプロジェクトの事故は21件すべて、
テストが緑のまま、実データか公開画面を見て初めて見つかりました。

### 直したのに画面が変わらない

push するとサイトは作り直されますが、**収集は走りません**（情報源を叩きすぎない
ための設計です）。仕分けの直しが公開データに入るのは**収集のとき**なので、
翌朝6時を待つか、手元で収集します。

```bash
python main.py collect
git add data out && git commit -m "chore: 収集 $(date +%Y-%m-%d)" && git push
```

### 情報源が0件になった（health に ✗ が出た）

その市町のサイトが作り替わって、RSS の置き場所が変わったのがほぼ確実です。
`config.yaml` でその情報源の行を探し、`feed_url` をブラウザで開いて確かめてください。

**慌てなくて大丈夫です。** 1つ止まっても他の情報源は動き続けるので、暦は止まりません。

### git が衝突した

毎朝ボットが `data/` と `out/` にコミットするので、**`git pull` を忘れると必ず起きます。**

```bash
git status       # 衝突したファイルを見る
```

衝突するのは `data/` と `out/` だけのはずです。**手元の承認を残して、機械の分を
捨てます**（承認・却下は人の判断で、収集は翌朝またやり直されるため）。

```bash
git checkout HEAD -- data out      # HEAD＝手元。自分の判断を残す
git add data out
git commit -m "chore: 手元の承認を優先して併合"
python main.py build               # out/ を作り直して辻褄を合わせる
git add out && git commit -m "chore: サイトを作り直す"
git push
```

ボットが集めたばかりの記事は捨てられますが、翌朝また集まります。
ただし **RSS の窓から落ちた記事は戻りません**（フィードは新しいものしか出しません）。
**防ぎ方は1つだけ。作業を始める前に必ず `git pull` すること。**

## 5. やらないこと

1年後の自分が「改善しよう」と思って壊す可能性があります。**一度試して失敗した道**を
並べておきます。

- **承認を自動化しない** — 公開物の品質を守る最後の砦。1日5分で済みます
- **`uid` の作り方を変えない** — 配信済みの `events.ics` を購読している人の
  カレンダーで、予定がいったん消えて別物として増えます
- **終わった催しを消さない** — 祭りが縮小し、統合され、途絶えていく過程は、
  ほかのどこにも残りません。それを残すことがこのサイトの存在理由の半分です
- **依存を増やさない** — 4つだけ。10年運用では、部品の少なさが最大の防御です
- **除外語を思いつきで足さない** — 実データで測ってから。1語入れただけで大田市
  最大の祭りが消えかけました
- **仕分け器を LLM に置き換えない** — 語の一覧は、実際に起きた誤判定の記録そのものです

**理由の詳しい話と、これまでに起きた事故の一覧は `CLAUDE.md` にあります**
（「譲れない設計判断」と「これまでに起きた事故」）。
**改善を思いついたら、手を動かす前にそこを読んでください。**

浜田・江津をはじめとする**石見地域の催しを自動で集めて、ひとつの暦にまとめて公開する**ツールです。

このツールは、その中から**催しだけを掘り出して並べます**。

もともと「山陰の蚤の市を集める」ツールとして作り、対象を地域イベント全般に広げました。
蚤の市版は `main_nomi.py` に残してあります。

## 3つの種別 — 時間軸が違うものを分けて扱う

同じ「地域の情報」でも、住民にとっての時間の意味が違います。ここを分けないと
一覧が使いものになりません。

| 種別 | 時間軸 | 並び順 | 表示 | 住民の動詞 |
|---|---|---|---|---|
| **催し** | 開催日 | 日付の昇順 | 8月9日(日) | 行く |
| **募集** | **締切** | **締切の昇順** | **締切まであと3日** | 申し込む |
| **制度** | なし | カテゴリ順 | 随時 | 使う |

- **募集だけ並び順が逆**です。締切が近いものほど上に来ないと役に立ちません
- **締切が14日以内のものがあるときだけ**、募集ブロックが催しより上に繰り上がります
- 催しにも申込締切があるので、開催日とは別に「申込締切 8/1・あと5日」を添えます

### 判定順序に意味があります

「出前講座を**ご利用ください**」は講座という催しの語を含みますが制度です。
そのため制度を最初に判定します。

1. 制度パターン（ご利用ください・派遣・貸出）→ **制度**
2. 催しの名詞（祭り・教室・展・コンサート）→ **催し**
3. 募集の語（募集・応募・締切・コンテスト）→ **募集**
4. それ以外 → 催し

「さざんか祭り アトラクション参加者**募集**」が**催し**になるのは意図どおりです。
本体は祭りで、募集はその一部だからです。

## 詳細ページからの日付抽出

RSSにはタイトルとリンクしかないので、開催日と申込締切は詳細ページを見に行って取ります。
実際のページを読んで設計したので、次の2つに対応しています。

**1ページに日付が7個あることがある**

江津市 Go-Con2026 のページには、掲載日／提出期限／公募期間／結果通知／勉強会×3／
最終審査会 の日付が並んでいます。本文を正規表現でなめると、最初に見つかる「掲載日」を
拾って完全に間違えます。

**市によって書き方がまるで違う**

| | 江津市 | 浜田市 |
|---|---|---|
| 構造 | 「提出期限」など見出しで区切られている | 見出しなしの流し込み |
| 有効な手法 | 見出しベース | 文脈語ベース（「までに」「午後1時～」） |

そこで2層構えにしています。

1. **見出しベース** — 「提出期限」「公募期間」「日時」などの見出しを見つけ、
   その直下の日付だけを取る（期間の見出しは終わりの日付が締切）
2. **文脈語ベース** — 見出しがない場合、日付の直後の語で判断する。
   「7月31日（金）までに」→締切、「12月13日（日）午後1時～」→開催日

**どこから取ったかを必ず記録します。** 承認画面に「見出し「提出期限」から取得」と
表示されるので、人が誤りに気づけます。根拠の見えない日付は、公開物では載せないほうが
ましだという考えです。

詳細ページを見に行くのは**仕分けを通過したものだけ**です（集めた全部ではありません）。
取得間隔は `config.yaml` の `fetch_delay_sec` で調整できます（既定1秒）。
各情報源に `fetch_delay_sec` を書けばそこだけ上書きできるので、robots.txt で
`Crawl-delay` を宣言しているサイトは、その情報源にだけ長い間隔を設定してください。

## 同一性の判定（uid）について

イベントの同一性は **URL** で判定します。タイトルや開催日は使いません。

v1.5で、uid に開催日を含めていたために事故を起こしました。日付抽出で開催日が
後から埋まった瞬間に uid が変わり、同じイベントが2枚並びました。同時に、締切だけ
取れたものは「既知」と判定され、抽出結果が捨てられていました。

**後から埋まる情報を、同一性の判定材料にしてはいけません。**
`tests/test_dedup.py` がこの事故の回帰テストです。

また収集時は、既知のものを飛ばすのではなく、**新しく分かった情報だけを追記**します
（人の承認・却下の判断は絶対に上書きしません）。

## 情報源は2種類ある

| 種類 | 例 | 性質 | 扱い |
|---|---|---|---|
| 市町の公式サイト | 浜田市 / 江津市 | ノイズ8〜9割。**申込・締切もの**が取れる | 厳しく仕分ける |
| 観光協会 | はまナビ / 江津市観光協会 | イベント専用RSS。**祭り・文化系**が取れる | `trust: high` で緩める |

観光協会のイベントカテゴリRSSには、そもそもイベントしか流れてきません。
自治体サイトと同じ厳しさで仕分けると、語彙にない催しを取りこぼすため、
`trust: high` を指定した情報源はしきい値を下げています。

## 終わったものの扱い

開催日・締切が過ぎたものは「これからの催し」から自動で外れ、ページ下部の
**畳んだ節「終わった催し・締切」に移ります。消しません。**

「今年はやらない」「最後の開催」も含めて記録として残す方針のためです。
過疎地では、祭りが縮小・統合・消滅していく事実そのものが、
他のどこにも残らない情報になります。

判定には気をつける点があります。

- **日付が分からないものは終了扱いにしない** — 勝手に消してはいけない
- **期間があるものは終わりの日で見る** — 「石見神楽定期公演（2026.4〜2027.3）」は
  開始日が過去でも開催中

## 日付の書き方は情報源ごとに違う

1市町ごとにCMSが違い、書き手も違うので、**表記の型は増え続けます。**
西暦・和暦（令和7年）・略記（R8.7.20）・見出し直下・流し込み・【】ラベル…と、
情報源を足すたびに新しい型が出てきました。

**いくつあるかは書きません**（すぐ古くなります）。
いまの一覧は **[CLAUDE.md](CLAUDE.md) の「日付表記は◯通りある」**にあります。

回帰テストは `tests/test_wareki.py` と `tests/test_extract.py` です。

**日付が取れないのは失敗ではありません。** 取れなかったものは
「日程は詳細ページで」と正直に出し、リンク先で確かめてもらいます。
カードの役目は気づかせることで、一次情報になることではないためです。

## カテゴリはタイトルを優先します

説明文まで見ると引っ張られます。実際に「ぶどうまつり」が **神楽・伝統芸能** に
分類されました。紹介文に「石見神楽の上演もあります」とあったためです。
祭りの紹介文はたいてい石見神楽に触れるので、この誤りは多発します。

タイトルで判定し、タイトルに手がかりがないときだけ説明文を見ます。

## 特徴

- **自治体RSSから自動収集**（RSSのURLはサイトから自動発見するので、市町を足すのが楽）
- **ルールベースの仕分け器** — 実データで測って調整（取りこぼしゼロを最優先）
- **承認キュー**（人が最後に見る） — 公開物の品質を守るため、あえて全自動にしていない
- **中止・終了を消さずに残す** — 「今年はやらない」も記録として残す設計
- **種別ごとに時間軸を分けて扱う**（催し／募集／制度）
- **年の推定は掲載日が基準** — 1月の記事の「3/8開催」は今が7月でも2026年3月
- 出力は 公開サイト(HTML) / events.json / events.ics

## 公開する

**[PUBLISHING.md](PUBLISHING.md) に手順をまとめています。**

公開前に `config.yaml` の `site.contact` を必ず埋めてください。空だとサイト上に
警告が出ます。「掲載をやめてほしい」という連絡を受ける窓口がないまま
自動収集サイトを公開してはいけません。

## 使い方

```bash
pip install -r requirements.txt
```

| コマンド | 何をする |
|---|---|
| `python main.py review` | 1件ずつ承認する（**日常はこれだけ**・1日5分） |
| `python main.py status` | 承認待ち・公開中・却下済み・手動掲載の件数 |
| `python main.py health` | 情報源が生きているか（最後の収集の記録を読む） |

- `--no-fetch` — 詳細ページを見にいかない（速いが日付が取れない）
- `--data-dir PATH` — 承認データの置き場を変える。**収集の変更を試すときだけ**
  （`data/` を複製して測る。常用しないこと）
- `--pages N` — フィードを何ページさかのぼるか

ネット接続なしで動きを見たいとき:

```bash
python demo_phase0.py    # 浜田市RSSの実データでパイプライン全体を通す
```

## 仕分け器の精度

浜田市などの実データを手でラベル付けして測っています。**数字は変わるので
ここには書きません。** 走らせれば、その場で出ます。

```bash
python tests/test_classify.py   # 再現率・適合率をいま測る
```

取りこぼしゼロを最優先にしています。公開物では「載っていない」ほうが「間違って載っている」より痛いため、
迷ったものは捨てずに承認キューへ送ります。

**分類器を変えたら必ず測り直してください。** 理由は [CLAUDE.md](CLAUDE.md) の
設計判断8にあります。

### 仕分けで効いているルール

実データから見つけた、間違えやすいパターン:

- **「募集」だけでは判定できない** — 入居者募集・委託事業者募集・指定管理者公募はすべてノイズ
- **「〜の様子を掲載しました」は過去の報告** — イベント語を含むので最も誤検出しやすい
- **「石見神楽」のような魅力的な語もノイズに混ざる**（例:保存拠点基本構想(案)）
- **RSSに数年前の記事が残っている** — 日付フィルタ必須（浜田市RSSに2022年のコロナ情報が残存）
- **催し名が英語のことがある** — DANCE CONTEST を一度取りこぼして修正
- **助詞が挟まると文字列一致が漏れる** — 「意見**を**募集します」「出場者**大**募集」。
  日本語は語の間に助詞や修飾が入るので、揺れやすいものは正規表現で持つ
- **実運用のノイズは8〜9割** — 自治体の公式サイトは、ほとんどが行政内部の情報。
  抜粋データで試したときより、実態はずっと厳しかった
- **RSSリンクは<head>にあるとは限らない** — 江津市は本文の<a>に3本並べていた。
  自動発見は本文も走査し、「新着」と書かれたものを優先する
