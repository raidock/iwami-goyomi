# 保存された分類と、保存された文の食い違い — 情報源によるタイトルの書き換え（2026-10-07）

- **測ったもの**: `data/` の4ファイルで、保存されている分類値（`score` `kind` `category`）と、保存されている `title`＋`description` からいまの分類器で計算した値が食い違う記事の原因
- **データ**: approved / pending / rejected / skipped の555件（`17777d3`）。git の履歴（`data/` に触れたコミット131件）と、情報源4つのフィードを1回ずつ取得したもの
- **結論**: 食い違いは14件。**分類器の更新が10件、情報源がタイトルや要約を書き換えたものが4件**。手で直したもの・説明がつかないものは0件

## 分け方

1. 各記事の分類値を**最後に書いたコミット**を、履歴から特定した
2. **そのコミット時点の `classify.py`** に、保存されている `title` と `description` を通した
3. 再現しなかったものは、情報源のフィードをいま取得して、いまのタイトル・要約と突き合わせた

| 原因 | 件数 | 根拠 |
|---|---|---|
| 分類器の更新 | 10 | 9件は、値を書いた当時の分類器で完全に再現した（その後の語彙追加で変わった）。1件はリポジトリの初版より前の値で、事故表1行目の頃の出力と一致する |
| 情報源の書き換え | 4 | 当時の分類器でも再現しない。いまのフィードの入力で計算すると、4件とも保存値と完全に一致する |
| 手で直した | 0 | 手作業のコミットは記事を別のファイルへ移しただけで、分類値の最終値を書いたものは無い |
| 説明がつかない | 0 | |

分類器の更新で古い値が残る仕組み（コードで確認）: 分類値が更新されるのは、その日のRSSに流れてきて、**かつ仕分けで drop にならなかった**ものだけ。
`cmd_collect` は drop を `ingest()` より前に捨てるので、いまの分類器で drop になる記事は、フィードに残っていても更新されない。

## 情報源による書き換えの4件

**なぜ起きるか**: `ReviewQueue.ingest()` は、既知の記事の分類値（`CLASSIFIED`）を、新しく取得したタイトル・要約で計算し直す。
一方、`title` と `description` は `FROM_SOURCE`（uid が同じなら同じ記事なので更新しない）なので、最初に見たときのまま残る。

**4件は下限です。** 見つかったのは「書き換えで分類が変わった」ものだけで、次の2つは数えられていない。

- 書き換えても分類が変わらないもの
- 「募集は終了しました」「【募集終了】」型の書き換え。`PAST_REPORT_TITLE` で drop になり `ingest()` に届かないので、分類値すら更新されない

全部を数えるには、全情報源のフィードを1回取得して、保存タイトルと突き合わせる必要がある（未計測）。

## タイトル・要約を更新する仕組みを入れたら、何が変わるか（コードで確認・実装はしていない）

| 対象 | 変わるか | 根拠 |
|---|---|---|
| `uid` | **変わらない** | `Event.uid` は URL だけから作る。URL が空のときだけタイトルを使うが、555件と手動掲載に URL が空のものは0件 |
| ICS の UID | **変わらない** | `{uid}@sanin-nomi`。`SUMMARY`（予定の題名）は新しいタイトルに変わる |
| 公開カードの見出し・検索 | 変わる（新しいタイトルになる） | `publish.py` がそのまま出す |
| 似たタイトルの警告 | 変わる | `review.py` の `title_similarity` が保存タイトルを比べる |
| 手動掲載との突き合わせ | 変わらない | URL（uid）で突き合わせる |
| 終了型の書き換え | **届かない** | 上のとおり drop で `ingest()` に来ない。更新の仕組みだけでは、締切終了の一部を拾えない |
| 「中止」への書き換え | 届くが、中止にはならない | `【中止】…` 型はタイトルだけで計算すると drop にならない（`募集を締め切りました` 型も同じ）。ただし `status`（開催予定 / 中止）は**人だけが変える項目**（`HUMAN_DECIDED`）なので、タイトルが変わっても `status` は変わらない |

**承認の意味について**: 承認後に機械が表示を変える前例は、すでにある。
日付（`REFRESHABLE`）は承認後も、毎回の抽出結果で上書きしている（`review.py` のコメント:
「日付は機械の抽出値、承認は人が下した判断で、性質が違う」）。
タイトルを更新しても、この線引き（人が決めるのは `review_state` と `status` だけ）は変わらない。
ただし、**人が見たときと違うタイトルが出る**のは日付と同じでも、タイトルは記事が**何であるか**を表すので、日付より影響が大きい。
同じ記事を使い回して開催日を書き換えるサイトは実在する（温泉津あさいち。ISSUES.md「繰り返しの催し」）。タイトルまで書き換えるかは確かめていない。
