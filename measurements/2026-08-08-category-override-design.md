# カテゴリ上書き機構の設計調査（2026-08-08）

- **調べたもの**: 天領さん公式・「市木市」のようにカテゴリが空のまま直せない
  記事を、`data/manual.json`とは別に「カテゴリだけ上書きする」仕組み
  （`data/overrides.json`のようなURL→カテゴリの対応）で救えるか
- **結論**: **作らない。** 実装コスト自体は小さいが、上書きの効果が
  「ラベル1行」にしかならない一方、`CLAUDE.md`が繰り返し警告している
  「変わる事実を2箇所に書く」問題（設計判断15）をカテゴリ判定に
  持ち込むことになる。件数（2件）が少ないうちは、直さない方が安全

---

## `manual.json`では天領さんを救えない（NEXT.mdの懸念どおり）

`collector/manual.py`の`merge_for_build`は、手動と同じURLが自動収集に来たら
**自動側を公開データからもキューからも除外する**（同じ記事を2回判断させない
ための設計）。天領さんは大田市公式サイト側で日付が実際に更新され続けている
（8/1掲載 → 8/4 → 8/30と、収集のたびに`date_start`が変わってきた実績が
`REPORT.md`に残っている）。ここを`manual.json`に移すと、**今後の自動更新が
止まる。** NEXT.mdの懸念は実装を見ても正しい。

## `approved.json`を直接書き換えても、次のcollectで消える

`collector/review.py`の`ReviewQueue.CLASSIFIED = ("kind", "tags", "category",
"score", "reason")`は、**分類器の出力を毎回そのまま上書きする**設計になっている
（コメント：「分類器は必ず答えを返すので空欄は『タグは無い』という答えその
もの」）。これは「締切あり」タグを廃止したのに2件残っていた事故・種別を
タイトル優先にしたのに古い値が残っていた事故を踏まえた意図的な仕様で、
**既知の記事のcategoryは、collectのたびに分類器の結果（空）へ戻る。**

つまり `approved.json` の`category`を手で書き換える一回限りの対症療法は
機能しない。上書きが効くには、**collectが書く`data/`には触れず、`build`が
サイトを生成する直前にだけ適用する**必要がある（`manual.json`が
`merge_for_build`で合流するのと同じタイミング）。

## `category`の実際の使われ道は1箇所だけ

コード全体を検索すると、`category`を参照しているのは
`collector/publish.py:148`の1行だけだった。

```python
cat = f"{_html.escape(ev.category)}・" if ev.category else ""
# → カード footer の「カテゴリ・掲載 2026/08/04」というラベル
```

並び順・フィルタ・検索・ICS出力のどこにも使われていない
（`events.json`には`to_dict()`経由で出るが、表示上の影響は無い）。

**副産物の発見:** `publish.py`冒頭のモジュールdocstringには
「制度　カテゴリ順」と書かれているが、実際の`_sort_key()`は
`ev.kind == "制度"`のとき無条件に`date.max`を返しており、
**カテゴリでは並んでいない**（安定ソートなので入力順のまま）。
テスト（`test_kinds.py`）もカテゴリ順を確認していない。
ドキュメントと実装が食い違っている可能性があるが、**今回は深追いしない**
（NEXT.mdの依頼範囲外。気になったら次回相談する）。

これにより、「カテゴリが空だと実害はラベルが無いことだけ」という
NEXT.mdの見立ては、コードで裏付けが取れた。

## 対象は実測2件、どちらも「載っている」ことは変わらない

`measurements/2026-08-08-tenryosan-category.md`のとおり、公開167件中
カテゴリが空なのは35件、うち「祭り・市・マルシェであるべき」と言えるのは
天領さん公式と「市木市」の2件だけ。どちらも催しとしては正しく載っており、
日付も取れている。

## 作らない方がよい理由

1. **効果とコストが釣り合わない。** 直るのはカード footer のラベル1行、
   対象は2件。新しいファイル形式・読み込み関数・書式チェック・テストを
   常設するほどの実害ではない
2. **「事実の二重管理」を作る。** `overrides.json`ができると、
   カテゴリの正解が「`CATEGORY_RULES`」と「`overrides.json`」の2箇所に
   分かれる。分類器側が将来語彙を足して正しく判定できるようになっても、
   上書きが優先され続け、**直った事実に誰も気づかない。** 古い上書きを
   見つけて消す仕組みが無いと、承認キューが2箇所に分裂した事故
   （設計判断7・15）と同じ形になる
3. **設計判断3の境界がぼやける。** 対象を「カテゴリだけ」に絞っても、
   一度「機械の判定を人が書き換える」経路ができると、次は`tags`や`kind`にも
   広げたくなる要求が出やすい。承認queueとは別の場所で人が判定に介入する
   前例を作ることになる

## 作るとしたらこの形、という記録だけ残す

将来、対象が増えて再検討するときのために設計だけ書いておく。

- 置き場は`data/overrides.json`1つ、形式は`{"URL": "カテゴリ名"}`のような
  素朴な対応表（`manual.json`のようなレコード全体ではなく、上書きしたい
  欄だけを持つ）
- 適用は`cmd_build`の中、`merge_for_build`の後・レンダリング直前。
  **collectでは読まない**（`data/`に書き戻すと`CLASSIFIED`の毎回上書きと
  競合するため）
- 存在しないURL・`CATEGORY_RULES`に無いカテゴリ名は`manual.py`の`_warn`と
  同じ形で警告し、その1件だけ無視する（公開全体を止めない）

## 次に検討する条件

**「祭り・市・マルシェであるべきなのに空」という実例が3件を超えたら
再検討する**（`ISSUES.md`の「繰り返しの催し」がmanual.json 3件を
閾値にしているのと同じ考え方）。いまは2件なので閾値に達していない。
