# 繰り返しの催しの測定と設計（2026-08-08）

- **測ったもの**: 公開167件（`approved.json` 161 + `manual.json` 6）で
  反復表現（`毎年` `毎月` `毎週` `第N曜日` `定期`）を含むものが何件か、
  そのうち実際に「単一の開催日が無い」ものは何件か、いま画面でどう
  見えているか、`Event`に何を足せば表現できるかを調べた
- **結論**: **実装しない。** 設計案は3つ検討し、やるなら軽量案（案B）
  が妥当という見立てだけ残す。実例がまだ3〜4件で、`CLAUDE.md`が繰り返し
  警告している「1〜2件を見て規則を作ると後から反例が出る」の水準に
  達していない

## いま画面でどう見えているか

`date_start`が無い3件（＋手動1件）は、`kind == "催し"`のまま
`collector/publish.py`を通ると:

- `_when_html()` → `<span class='tbd'>日程は詳細ページで</span>`
- `_sort_key()` → `date.max`（開催日の近い順という並びの**最後尾**に沈む）
- `is_past()` → 終了日（`date_end`/`date_start`）が無いので常に`False`

**つまり畳まれることは無い代わりに、「これからの催し」の一番下に
ずっと残り続ける。** これは`ISSUES.md`の「日付が無いまま古い記事が
『これから』に残っている」と同じ表示だが、**原因は別**（あちらは単発記事が
窓の広い収集で古いまま入った話、こちらは繰り返しの催しの構造そのものが
単一日を持たない話）。

催し153件のうち`date_start`が無いものは29件（19%）で、うち今回の
「繰り返しで単一日が無い」形に該当するのは4件（手動含む）だけだった。
**残り25件は`measurements/2026-08-07-28-undated-events.md`で別に診断済みの
理由による。** 繰り返しは「日付が取れない」問題の主要因ではない。

## 江津市石見神楽定期公演は、モデルを変えずに直る可能性がある

「2026.4〜2027.3」は**モデル上は既存の`date_start`〜`date_end`の期間表現で
そのまま持てる**（`CLAUDE.md`の「石見神楽定期公演 2026.4〜2027.3は開始日が
過去でも開催中」という記述どおり、期間ものとして扱う前提は既にある）。
**足りないのは`extract.py`側が`YYYY.M〜YYYY.M`という表記を年間期間として
読む型を持っていないことで、これは`Event`にフィールドを足す話ではない。**
実例はいまのところこの1件だけなので、抽出の型を1つ足す判断も
`CLAUDE.md`の「実例が増えてから測る」基準に照らして時期尚早と考えられる。

## `Event`に何を足せば表現できるか（設計案・実装しない）

`recurrence`は現時点でコードに存在しない（前回確認どおり）。3案を検討した。

### 案A: 何もしない
現状の「日程は詳細ページで」表示のまま。催しの存在は伝わる
（`CLAUDE.md`「日付が取れないのは失敗ではない」の哲学と一致）。
欠点は、サヒメルのように**単一の次回日付だけ拾えるケースで、
毎月・毎年、人が同じ判断を繰り返す**負担が残ること。

### 案B: 軽量な「繰り返しの説明」フィールドを足す
- `recurrence_note: Optional[str]` — 抽出した頻度表現をそのまま
  文字列として持つ（「毎週土曜日開催」「毎年7月の第3土曜日」など、
  構造化しない）
- 表示側は、`date_start`が無く`recurrence_note`があるときだけ
  「日程は詳細ページで」の代わりに「毎週土曜日開催・詳細は
  詳細ページで」のように出す
- **次回の日付は計算しない。** 規則パーサを持たないので依存が増えない
  （設計判断6と両立）。並び順（`date.max`で最後尾）は変えない。
  表示の一文が変わるだけの最小案

### 案C: 規則的なものだけ次回日付を計算する
- 「第N曜日」「毎年M月D日」のように機械的に計算できる表記だけ
  `next_occurrence()`のような関数を実装し、`date_start`を自動算出する
- 効果は大きい（3件が正しい位置に並ぶ）が、規則パーサ・祝日振替や
  記事の更新漏れへのフォールバックなど周辺ケースが増える。
  **実例3件では規則の網羅性を測る材料として少なすぎる**
  （`CLAUDE.md`「1〜2件を見て規則を作ると後から反例が出る」と同じ形）

## まとめと所感

| 案 | 効果 | コスト |
|---|---|---|
| A（何もしない） | なし | ゼロ |
| B（説明文フィールド） | 表示の違和感が減る。次回日付が無くても「繰り返しである」ことは伝わる | フィールド1つ＋表示1箇所の分岐。小さい |
| C（次回日付を計算） | 3件が正しい位置に並ぶ | 規則パーサとフォールバックが要る。実例が少なく網羅性を測れない |

**やるなら案B が妥当**という見立てだが、実例はまだ3〜4件で、`ISSUES.md`
がすでに書いている「町を足して実例が増えてから」という見送り方針を
覆すほどの材料は今回も出なかった。**実装はしない。** 次に実例が増えたとき
（4件→5件、あるいは町が増えて新しい形が出たとき）に、この測定を
出発点として再検討すればよい。
