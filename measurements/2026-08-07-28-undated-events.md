# 日付が取れない28件の診断（2026-08-07）

- **測ったもの**: 「これから」に残る催し28件（date_start無し）の詳細ページを、実際に1件ずつ取得して原因を分類
- **データ**: 公開中の全28件。`requests` + 本番の `collector.extract.extract_dates()` を実際のHTMLに対して実行し、各記録の実際の `published_at` を基準日として使用（本番と同じ挙動になることを確認ずみ）
- **結論**: **実装しない**（指示どおり）。原因は10種類に分かれ、**うち1件は「見つからない」ではなく「間違った日付を拾っている」誤抽出**。効果が大きい割に安全に直せそうなのは1〜2件で、残りは実例が少なすぎるか、直すと別の壁にぶつかる

## 最優先で見てほしいもの: 誤抽出（#10・大田市農業体験プログラム）

**見つからないのではなく、間違った日付を「締切」として持っています。**

```
募集期間：８月２６日まで！（７月３０日追記）
```

正しい締切は **8月26日** ですが、いま公開データに入っているのは **7月30日**
（「追記日」＝更新履歴の日付）です。`extract.py` の `PERIOD_HEADS` 処理が
`dates[-1][0]`（見つかった日付の**最後**）を締切として採る作りのため、
本文中で後に出てくる「（7月30日追記）」を拾ってしまいます。

```python
elif not got.deadline and any(k in name for k in PERIOD_HEADS):
    got.deadline = dates[-1][0]          # 期間は終わりが締切
```

**「（◯月◯日追記）」は役所のページでよく使う言い回し**（今回の27件中でも
複数のページで見かけました）ので、同じ形が他のページにも潜んでいる可能性が
あります。**日付が無いより、間違った日付がある方が悪い**（CLAUDE.md
「公開物では載せないほうがまし」）ので、実害としてはこの1件がいちばん重いです。

いまはこの記録の `deadline` が既に過去（7/30）なので画面には実害が出ていません
（募集ブロックの最後尾に沈んでいるだけ）が、**正しい8/26のうちに気づけなかった**
ということでもあります。

**直し方の方向性（実装はしていません）**: 「追記」「更新」という語の直前・直後の
日付を候補から除く、あるいは PERIOD_HEADS では「まで」「〜」に隣接する日付だけを
採る、などが考えられますが、**他のPERIOD_HEADS該当ページに実害が無いか測ってから**
にすべきです。

## 新しく見つかった壁: 見出しが構造化されていない（#2・#12）

**同じ「しまねふるさとフェア２０２７」の告知記事が、浜田市（#2）と大田市（#12）
それぞれの公式サイトに別々に載っており、両方とも同じ理由で開催日が取れません。**

- 浜田市: 「令和9年1月23日(土)～24日(日)」が書かれているが、ページ全体が
  `<address>` タグだけで組まれていて、見出しらしい行（「○今年度の開催日程」）も
  本文と同じ `<address>` タグ。`_sections()` は `h2〜h6/th/dt/strong/b` タグしか
  見出しと認めないので、そもそも見出しとして拾えない
- 大田市: 「２０２７年1月23日（土）10時～17時、1月24日（日）10時～16時30分」が
  `<h2>開催要項</h2>` の直後の平文段落「３．開催日時」に書かれている。
  `<h2>` はあるが、その中身を「１．」「２．」「３．」と**書き手が手で番号を振った
  ただの`<p>`**で区切っており、`_sections()` からは「開催要項」という1つの
  見出しの中身にしか見えない。「開催要項」はどの見出し語にも一致しない

**どちらも「サイトが構造化されているように見えて、実際は平文」という、
設計判断14（構造化されていても、それが何を指しているかは別）に近い形の話です。**
ただし今回は「意味を取り違えた」のではなく「そもそも見出しとして認識できない」
という一歩手前の問題です。

**直すなら影響が広い可能性があります。** 浜田市・大田市はどちらも公式サイトの
CMSで、同じ書き方（平文の番号付き段落・`<address>`タグの多用）が他の記事にも
使われていると考えられます。ただし「見出しらしい行」を見た目（記号・番号・
文字数）だけで判定すると、日付と関係ない番号付き段落まで拾って誤爆するリスクが
高く、**実データでどれだけの記事がこの形かを測ってからでないと危険**です。

## 効果が小さそうなもの（実例1件・優先度は下げてよい）

- **#11「応募期日」**: `DEADLINE_HEADS` に無い言い回し。`応募期限` は既に登録
  済みなので語として近く、足せば安全に直りそうですが、実例はこの1件だけです
- **#1「締切は8月21日（金）となっております」**: 日付の**前**に「締切」が来る
  文中パターン。いまの層2は日付の**後ろ**に来る語（まで／必着など）しか
  見ていません。もう1件（後述の#8）と合わせて、日付の前後どちらに手がかりが
  来ても拾える形にする余地はありますが、実例は2件だけです
- **#8「が8月1日（土曜日）に開催！」**: 日付の直後に「開催」が来る想定は
  既にあります（`_HELD_TAIL`）が、実際は「（土曜日）**に**開催」と助詞が
  挟まるため一致しません。この記事の開催日（8/1）は既に過去なので、
  直しても実害の解消にはなりません
- **#17「10/12 市木市」**: タイトル冒頭の日付は `8月22日（土）` のような
  漢字表記しか対応しておらず、スラッシュ表記（`10/12`）は非対応です。
  ただし**この記事自体、情報源のサイト側に「過去のイベント」ラベルが
  ついています**（10か月前の記事）。直しても2025-10-12という過去の日付が
  付くだけで、畳んだ節に移る以外の効果はありません
- **#17（本文側）「10月12（日）10：00〜15：00」**: 「日」が欠落しているため
  日付として認識されません。これが**4-aそのもの**です。タイトル側と本文側の
  両方に別々の壁があるので、**どちらか一方を直しても他方が残ります**

## 直さないほうがよいもの

- **#26「開園期間：2026年7月20日〜」**（津和野ブルーベリーファーム）:
  開始日だけを拾うと、**終了日が無いので `is_past()` が翌日から過去と
  判定してしまいます。** 温泉津あさいちと同じ罠です。開始日だけの記録は、
  拾わないほうが「これから」に長く残って実害が小さい、という逆転現象が
  起きます。ラベル自体（`開園期間`）を `SELF_PERIOD_HEADS` に足す前に、
  この副作用への対処（例: 終了日が無い開始日は `is_past` の対象にしない）
  が要ります
- **#3 就学時健康診断・#20 夜神楽公演・#24 町政運営説明会**: 会場や回ごとに
  日付が違う「巡回展」と同じ形です。どれを代表の1日にするかが決まらないので、
  実例が増えてから設計する方針（ISSUES.mdの巡回展の項）のままでよいと思います。
  ただし**#24（町政運営説明会）は3回とも既に終わっています。** 拾えなくても
  実害はいまは無いですが、`is_past()` が日付不明を過去にしない設計（設計判断4）
  の結果として、終わった催しが「これから」に残り続けている実例です
- **#4・#5・#15・#16「毎年◯月◯日」型**: ISSUES.mdの「繰り返しの催し」に
  既に書いてある内容そのものです。新しい情報はありません
