# 承認ミスの記録（2026-08-09）

**これはコードの測定ではなく、運用側（人の判断）が誤った記録です。**
「人が間違えた」こともコードのバグと同じ価値がある、という考えで残します。

## 何が起きたか

承認作業（`python main.py review`）で、川本町観光協会の2件を `y`（公開）に
した。どちらも実際には**2025年の催し**で、今年の「これから」には入らない
ものだった。

```
【12/20開催】島根フィルティーズ ファン感謝祭      掲載 2025/12/12 → 2025年12月20日
【11/14,15開催】弓ヶ峯八幡宮「秋の例大祭」        掲載 2025/10/21 → 2025年11月14・15日
```

## なぜ間違えたか

- タイトルの `12/20` `11/14,15` を見て、**今年の開催だと思い込んだ**
- `date_start` が空欄で「日程は詳細ページで」と出ており、正しい日付が
  どこにも表示されていなかった
- **承認画面（`review_cli`）に掲載日が出ていなかった。** URLには
  `/2025/` と入っていたが、見落とした
- **日付が取れていないカードほど、判断材料が少ない。** 皮肉なことに、
  日付が取れなかった原因（下記）そのものが、人の誤判断も誘発していた

## 対処した内容

| 対応 | 内容 |
|---|---|
| 【125】却下し直す | 承認済みの2件を`rejected.json`に戻した |
| 【126】原因を直す | タイトルの日付表記が10通り目「【】の中にスラッシュ日付」だったため未対応だった。実装し、既存の該当4件にも遡って適用（うち2件は実際に終了済みで、日付が付いたことで正しく畳まれた） |
| 【127】隣接案を測定 | 「掲載日から半年経過なら終了とみなす」も提案されたが、実データで測ると4件中2件が実際には継続中で危険と判明。**実装しなかった** |
| 【128】再発防止 | `pending`・`review`画面に掲載日を表示するようにした。次に同じ状況が起きても、掲載日を見れば気づける |

## 残る教訓

- **日付が取れていない＝安全ではない。** 「日程は詳細ページで」のカードは、
  抽出に失敗しているだけで、実際には過去のものが混ざりうる
- **承認画面の情報量が、承認の正確さを決める。** URLに`/2025/`と書いてあっても、
  画面の主要な位置（掲載日）に出ていなければ見落とす
- 詳しい経緯は`CLAUDE.md`の事故表（「承認者が去年の催し2件を『これから』と
  誤判定して承認した」の行）にも記録した
