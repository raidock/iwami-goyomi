# JSON-LD（Event構造化データ）と sitemap.xml の調査（2026-08-06）

- **測ったもの**: `schema.org/Event` を出力すれば Google のイベント検索に載るか。
  出せるならどこまで。sitemap.xml は要るか
- **データ**: 公開165件（Googleの公式ガイド [developers.google.com/search/docs/appearance/structured-data/event](https://developers.google.com/search/docs/appearance/structured-data/event) と突き合わせ）
- **結論**: **Event構造化データは実装しない。** 日付が無い28件だけの問題ではなく、
  **会場の住所とページ構成という、もっと根本的な2点で条件に合わない**

---

## Googleの必須条件（公式ガイドより）

| 項目 | 必須か | 内容 |
|---|---|---|
| `startDate` | **必須** | ISO-8601。時刻が無いなら日付だけでよい（`"2026-08-08"`） |
| `location.name` | **必須** | 会場名 |
| `location.address`（`PostalAddress`） | **必須** | 番地・市区町村・郵便番号・都道府県・国の構造化データ |
| ページ構成 | **必須** | **「各イベントは専用URL（リーフページ）を持ち、そのURLでマークアップすること」**。**一覧ページへのマークアップは非推奨**、公式に「一覧ページではなく、催しごとの投稿ページにマークアップを足すことを勧める」と明記 |
| `endDate` `description` `image` `organizer` など | 推奨（無くても失格ではない） | |
| バーチャルイベント | **対象外** | 「実在の場所を伴わない仮想体験は非対応」 |

## 実データとの突き合わせ

| 項目 | 持っている件数 | 石見暦の実情 |
|---|---|---|
| `startDate`（催し150件中） | 122件（81%） | 28件は「日程は詳細ページで」。ここは Takao さんの見立てどおり除外すれば済む |
| `location`（venue） | **150件中5件（3%）** | **すべて `data/manual.json` の手動掲載。自動収集は0件** |
| 構造化された住所（番地・郵便番号など） | **0件** | venueがある5件も自由記述の1行（例:「浜田漁港一帯（浜田市原井町）」）で、`streetAddress` / `postalCode` に分解できる形になっていない |
| 催しごとの専用URL（自サイト内） | **0件** | `url` は情報源（市サイト・観光協会）へのリンクで、**石見暦自身がその1件のためのページを持っていない** |

## なぜ「28件を除けば出せる」では済まないか

Googleの条件は AND です。**`startDate` があっても、`location.address` が無ければ・
一覧ページにしか置けなければ、条件を満たしません。** いまの石見暦で全部を満たす
記録は0件です（venueがある5件も、構造化住所と専用URLの両方が無い）。

**一覧ページ非推奨**が特に重い制約です。石見暦は `index.html` 1枚に165件を並べる
設計そのもの（catalog的な性格）で、これを崩して催しごとのページを作ることは:

- 依存を増やさずには作れる（静的HTMLを追加で書き出すだけ）が、**運用の手間が
  件数分に比例して増える**（いまは1ページの再生成で済む）
- 会場の構造化住所を作るには、**自由記述の venue を番地・郵便番号まで
  分解する新しい処理**が要る。ジオコーディングAPIを使うなら依存が増える
  （設計判断6）。手作業で当てるなら、承認作業とは別の新しい人手仕事になる
- 一次情報にリンクする設計（設計判断12「本文は転載しない」）と、
  「催しごとの自サイトページを持つ」設計は方向がやや逆で、
  石見暦を情報の**転載元**寄りに近づける

## 募集・制度はもっと難しい

- **募集14件**: 「地域おこし協力隊の募集」「ふるさと納税の事業提案募集」
  「グラフコンクール作品募集」など性質がばらばらで、単一の schema.org 型に
  当てはまらない（`JobPosting` が合うものと合わないものが混ざる）
- **制度1件**: 実例が1件しかなく、型を作る材料が無い（`ISSUES.md` の
  「実例が集まってから」と同じ理由）

## sitemap.xml

**ページが実質2枚**（`index.html` と `about.html`）なので、
発見のための効果はほぼ無い（2ページ程度なら通常のクロールで十分見つかる）。

出す価値があるとすれば「毎朝内容が変わる」ことを `lastmod` で伝えて再クロールを
促す点だが、**告知前でリンクがまだ無いいまの段階では、Googleが自発的に
高頻度で見に来る動機が薄い。** 実装コストはほぼゼロ（`out/` に静的XMLを1つ
足すだけ）だが、いま急いで作る理由も無い。

**結論: 作るなら安いが、優先度は低い。** ドメイン確定後、告知の直前くらいで
十分。

## 石見暦で現実的な構造化データ

Event ではなく、`ItemList`（一覧であることそのものを示す型。必須項目が緩い）や
`WebSite` 程度なら、いまのデータでも無理なく出せる。ただし **Event のような
検索結果の見た目（日時・会場つきのリッチリザルト）にはならない。** 効果は
限定的なので、いま急いで作る理由は無いと判断した。

## なぜ残すか

結論が「実装しない」なので、コードにもテストにも痕跡が残らない。
次に「JSON-LDを足しては」という話が出たとき、**「venueが無い」だけでなく
「一覧ページ自体がGoogleの想定と合わない」という、より大きい制約から
説明できるように残す。**
